# Experiments

Each dated folder is a self-contained write-up with the scripts, raw data, graded predictions and plots behind its conclusions.

| Folder | Question | Outcome |
|---|---|---|
| [`2026-11-23_generalization/`](2026-11-23_generalization/README.md) | Does copy + one-pass diffusion drafting (DFlash) beat every single drafter end to end in a real serving engine, and does it generalize? | vLLM plugin `copyflash` (copy unchanged code, DFlash for new code, lossless). Qwen3-8B on an H100, 261 code edits: 9.04× over plain AR (95% CI 8.4–9.7), 1.34× over DFlash. Held-out Qwen3-4B: 8.81×. Small gain on bug fixes (1.02×) and diffs (1.10×). The speedup grows from 6× to 19.5× with the share of unchanged code. |
| [`2026-11-22_h100-bench/`](2026-11-22_h100-bench/README.md) | Matched vLLM benchmark of speculative decoders on code edits (Qwen3-8B, run on an A100). | Over plain AR: DFlash 6.97×, prompt lookup 4.53×, EAGLE-3 3.18×, 0.6B draft model 2.84×. Copy + DFlash router 1.33× over DFlash in a PyTorch harness. A performance law predicts held-out latency within 6–15%. |
| [`2026-11-21_dflash-mlx/`](2026-11-21_dflash-mlx/README.md) | How much new code inside edits does a one-pass diffusion drafter get right, compared with small AR drafters? (Mac, MLX) | DFlash accepts 3.0–4.7 tokens per guess on new code. At equal cost, one-pass drafting beats AR drafters (EfficientEdit-style) by 16–60%. |
| [`2026-11-21_copy-audit/`](2026-11-21_copy-audit/README.md) | Where do target calls go when unchanged code is copied during edits? (Mac) | New code is 8–14% of tokens but about two thirds of target calls, so the drafter for new code decides the speedup. Resyncing the copy adds only 9–19%. |
| [`2026-10-12_gpu-session/`](2026-10-12_gpu-session/README.md) | H100 session: prompt caching, longer training, step distillation; matched-size diffusion vs. AR; CPU + GPU latency. | At matched size (150M, 10 epochs) diffusion matches/beats AR (exec 0.562 vs 0.527, exact 0.324 vs 0.250). GPU: diffusion 23 ms vs. vLLM AR 63 ms (larger model, +13 points). CPU: 216 ms vs. llama.cpp AR 304 ms. |
| [`2026-10-09_fair-cpu-benchmark/`](2026-10-09_fair-cpu-benchmark/README.md) | Same-engine CPU comparison of diffusion vs. AR, plus cheap inference wins. | Cheap changes make diffusion 2.1× faster on CPU (863 → 415 ms). Schema verification adds +6.5 points exec. On CPU a 3.3× larger AR model still matches diffusion fp32 latency at +14 points accuracy. |
| [`2026-07-05_qwen-ar-diffusion/`](2026-07-05_qwen-ar-diffusion/README.md) | AR vs. masked diffusion on the same base model (Qwen2.5-Coder-0.5B) and data. | AR wins on quality (0.645 vs 0.191 semantic). The 150M ModernBERT diffusion model reaches 0.500, so bidirectional pretraining matters more than size. Diffusion is ~2.4× faster on H100 but slower on a Mac. |
| [`2026-06-30_papl-ab/`](2026-06-30_papl-ab/README.md) | Does PAPL (planner-aware, confidence-reweighted) fine-tuning improve the ModernBERT diffusion model? | Only speed: ~7% fewer steps under adaptive early stop, same accuracy. Real quality is ~0.50 semantic (exact match undercounts it). Invalid SQL is the biggest failure mode. |
| [`2025-06_v0-from-scratch/`](2025-06_v0-from-scratch/) | First prototype: a small transformer trained from scratch with the GPT-2 tokenizer. | Superseded. Too small to generate useful text, which led to fine-tuning pretrained MLMs (RoBERTa, then ModernBERT). |

Decoding-strategy comparisons (confidence vs. dependency ordering, fixed vs. adaptive steps) are documented in the main [README](../README.md#decoding-efficiency-steps-vs-autoregressive).
